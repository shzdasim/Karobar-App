# Karobar missing-feature audit

Reviewed: 13 October 2026.

Feature #3 update: sale availability validation and product/batch locks are implemented for create/edit/delete. See [sale stock safeguards](sale-stock-safeguards.md) for scope and verification.

Feature #2 update: new-sale cost snapshots are implemented without changing existing profit formulas. Legacy records remain estimated without backfill. See [saved sale costs](sale-cost-snapshots.md).

Implementation update: feature #1, multiple deliveries against one purchase order, is now implemented and tested. See [the purchasing workflow update](purchase-order-workflow.md#multiple-receipt-update--13-october-2026). The original findings below are retained as the audit baseline.

## Scope and confidence

This is a repository review of frontend routes, pages and forms, API routes, controllers, models, migrations, services, scheduling, reports, print templates, tests and purchasing documentation. It is not a live browser walkthrough or a production-data audit. “Missing” means no implementation was found in this repository; external services or deployment automation may provide capabilities not visible here. No application behavior was changed and tests were not rerun for this documentation review.

Priorities are proposed for the app's stated retail, wholesale and trading use cases. P1 means address before relying on the app for the relevant daily workflow; P2 means a useful next extension; P3 means conditional on business needs. These are product priorities, not a claim that every business needs every feature.

## Already implemented — do not duplicate

- Retail and wholesale sales, customer-specific wholesale prices, invoice editing and printing.
- Purchases, paid/bonus quantities, discounts, taxes, batches and expiry fields.
- Sales and purchase returns, stock adjustments, product/category/brand management.
- Customer and supplier ledgers, manual/payment entries, invoice settlement and ledger rebuilding.
- Purchase forecasting, demand tracking, saved purchase orders, expected receiving dates, order cancellation and invoice conversion.
- Low-stock notifications, near-expiry reporting, dashboard KPIs and sales/product reports.
- Master-data CSV import/validation/export, bulk product actions.
- Users, roles, permissions, password reset, licensing, themes and printer settings.
- Manual database/settings/full backups, download, upload, restore and retention cleanup.
- Barcode storage/import/search already exists; barcode capability as a whole is not missing.

Evidence: [API routes](../routes/api.php), [frontend routes](../resources/js/routes/index.jsx), [models](../app/Models), [print templates](../resources/views/printer), [purchase order workflow](purchase-order-workflow.md).

## Suggested implementation order

1. Protect existing records: authoritative totals, stock locking/availability, linked return limits and sale-time cost snapshots.
2. Complete purchasing: multiple PO receipts, remaining-value reporting and overdue receipts.
3. Protect work and trace changes: recoverable drafts, audit history, void/reversal controls and scheduled off-server backups.
4. Complete money workflows: payment events/methods/allocations, cashier shifts, credit terms/aging, expenses and cash/bank tracking.
5. Improve inventory operations: reorder policies, stocktake, expiry allocation, quarantine and movement reconciliation.
6. Add commercial extensions based on actual demand: quotations/delivery, supplier catalogs, sharing and deeper analytics; branches/offline/accounting only with explicit scope.

## Review limitations and follow-up verification

- Absence findings were cross-checked against route, model and migration inventories and targeted source searches; they do not prove that an external integration or operational process is absent.
- The stock, totals, returns and historical-cost findings are source-level control gaps. They should receive focused API/concurrency tests and scenario verification before changes; this audit did not reproduce production failures.
- Existing tests mainly exercise purchasing workflow, login/product searches and forecast arrangement. Broader sale/return/payment/stock consistency and browser/print regression coverage would support the priorities above; test coverage is an engineering gap rather than a customer feature.
- README statements about warehouse readiness, cash/bank accounts and profit-and-loss need alignment with the implemented workflows. Update it when scope is agreed to avoid promising unimplemented capabilities.
